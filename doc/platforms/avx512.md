# AVX-512

AVX-512 is a family of extensions, not one feature. miraculix gives every
sub-extension its own token, so a CPU with only part of the family still
gets the parts it has. Part of the [x86 module](x86.md).

## Which token do I need?

| You need | Token | Notes |
|---|---|---|
| 512-bit f32/f64/i32/i64 | `Avx512f` | the base |
| 512-bit i8/i16 | `Avx512Bw` | 128/256-bit byte ops are already on SSE2/AVX2 |
| 128/256-bit forms of AVX-512 ops | `Avx512FVl`, `Avx512DqVl`, `Avx512VbmiVl`, ... | each `Vl` token proves the extension **and** VL |
| `mullo` i64 | `Avx512Dq` | |
| Byte permutes (`vpermb`, `vpermi2b`) | `Avx512Vbmi` | `permutexvar_u8x64`, `permutex2var_u8x64` |
| Byte compress/expand, funnel shifts | `Avx512Vbmi2` | |
| INT8 / INT16 dot products | `Avx512Vnni` | |
| bfloat16 / FP16 | `Avx512Bf16`, `Avx512Fp16` (+ `Vl`) | FP16 needs rustc 1.94 |
| Mask registers (`k0..k7`) | `kmask::{bridge, logic, shift, ktest, build}` | `movepi8_mask -> u64`, `movm_epi8`, `kand`, `kshift`, `ktest` |
| The whole x86-64-v4 bundle | `bundles::V4` with `avx512_v4_fn!` | |
| Xeon Phi 4FMAPS / 4VNNIW / ER / PF | behind the `phi-asm` feature | discontinued hardware |

AVX10 is exposed through `x86::Avx10` (presence and version) and
`x86::ops::avx10::fp8`.

## OS support

A CPU can have AVX-512 while the OS keeps the ZMM / opmask state switched
off (some VMs and kernel configs). miraculix only reports AVX-512 when the
`XCR0` register says the OS saves that state, so tokens are `None` there.
On Intel Macs the kernel enables the state lazily, so miraculix asks it
directly (`hw.optional.avx512f`, kernel >= macOS 12.2) instead of reading
`XCR0`. See [detection](../detection-and-caching.md#what-detection-checks).

## 512-bit vs 256-bit

`auto_up` and `reduce` take the 512-bit path whenever `Avx512f` is present.
On older Intel server parts (Skylake-SP, Cascade Lake) sustained 512-bit
work can lower the clock. Zen 4 executes 512-bit ops as two 256-bit halves
without that penalty. If it matters for your workload, use `Avx2` tokens and
`avx2_fn!` kernels directly instead of `auto_up`.

## Kernels

Wrap multi-op AVX-512 bodies in `avx512f_fn!`, `avx512bw_fn!`,
`avx512vl_fn!`, `avx512_v4_fn!`, ... with the proving token as the first
parameter. See [kernel macros](../kernel-macros.md).
